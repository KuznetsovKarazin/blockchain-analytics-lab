# Data sources

All raw data live under `data/raw/` and `data/cache/`, which are git-ignored.
Nothing in this repository redistributes Elliptic, ethereum-ponzi or other
third-party labels; `results/` holds aggregate metrics (figures are regenerated by the
scripts and not distributed), with one
exception: S2 writes a per-incident table parsed from the DeFiHackLabs README
(`results/security/s2_v1/incidents.csv`: date, title, stated cause, parsed loss,
our two codings), distributed with attribution under the source's licence.

## AWS cache specifications

See `SPECS` in `scripts/d0_cache_aws.py`: Ethereum and Bitcoin block headers
2023-01-01 to 2025-12-31; Ethereum transactions for the weeks 2022-07-25 to
2022-07-31 and 2024-03-04 to 2024-03-10; Ethereum contracts (deployed bytecode)
created 2015-07-30 to 2017-12-31; Ethereum call traces 2025-02-07 to 2025-03-07
filtered to successful delegatecalls and value-carrying calls (`traces_slim`), and
Ethereum token transfers of 2025-02-21 (C1). Only the listed columns are kept.
Reading a date range from the cache fails if a day is missing, unless the cache
index marks it as missing upstream.

## Known encodings in the AWS Ethereum tables

* `to_address` of contract creations is the literal string `"None"`, not null.
* `value` is stored as floating point. Above 2^53 wei (about 0.009 ETH) not every
  integer is representable, so such values may be rounded; about 40 percent of
  transactions exceed this range, which bounds, but does not measure, the share
  actually rounded.
* Failed transactions (`receipt_status = 0`) carry a `value` that was never
  transferred; D1 keeps successful value and failed attempts as separate features.
* In `token_transfers`, `from_address` and `to_address` may be 32-byte
  left-padded; C1 keeps the last 40 hex digits.
* Missed slots after the Merge appear as gaps in block timestamps (12 s grid).

These are audited by D1 (`results/data/d1_v1/audit.csv` and `blocks_hygiene.json`).
