# Manuscript note: code identity, dispatch state and observation coverage

Operational evaluation requires separate evidence for entrypoint code identity, state-dependent dispatch and observable activity. In bounded Li.Fi discovery over `[2022-02-19, 2022-03-21)` UTC, the entrypoint diamond had the same reported code hash at both window checkpoints. However, 14 of 23 shared selectors named different facet addresses. Historical code observations showed different full destination runtimes for all 14 changed bindings. All four facet addresses shared by the endpoint enumerations returned identical code at those samples. These findings concern sampled identities; full-runtime differences, including metadata, do not alone establish different execution semantics.

We obtained 19 address–checkpoint code observations across 14 addresses, using 18 new responses and one retained response. Exact comparison with all 36 nonempty runtime objects in a previously independently reproduced compiler output yielded 11 matches at six addresses, extending source/runtime bindings to five additional addresses without recompilation. Eight addresses remained unmatched within that retained output. These bindings support focused source review but do not establish continuous code identity or exhaustive storage-writer coverage.

Across both attempts, 21 RPC requests retained 154,743 response bytes; no event chunk completed or replay occurred. Missing history was not treated as an empty event list or case exclusion. This evidence motivates explicit provenance for population and observation assumptions. Fixed-address workload statistics and complete protocol-routing claims require different supporting evidence.
